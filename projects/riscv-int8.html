Fused INT8 Dot-Product Accumulation in a Two-Read-Port RISC-V Core

  • In progress
  • RTL simulation
  • Implementation timing

Results cover one complete convolution layer; full-network inference and board measurements remain future work.

Integrated a four-lane signed INT8 dot-product accumulation instruction into the five-stage SiMPLE RV32I core, reusing two read ports through operand collection and evaluating the design on a complete MobileNet Visual Wake Words pointwise convolution layer.

Design study

Three source operands. Two register-file read ports.

DOT4ACC needs two packed INT8 inputs and the old destination value. The design question is how to collect that third operand correctly while retaining two read ports, and what fused accumulation gains on a complete operator.

  1. Check and preserve inputs

    Check RAW dependencies for all three sources, capture rs1 and rs2, hold IF/ID and insert a control bubble during collection.

  2. Reuse a port for the accumulator

    The pending state selects old rd on a read port while preserving the two captured packed inputs.

  3. Execute and write back

    Perform four signed INT8 multiply-accumulates and commit through the existing MEM/WB path and single write port.

One complete layer. Three controlled designs.

A uses the existing DOT4 hardware followed by ADD. B fuses accumulation with two read ports. C performs the same fused operation with three read ports.

The workload is one complete pointwise convolution layer, op8 of an INT8 MobileNet VWW model. These are simulation and OOC implementation results, not board measurements.

Design decisions

Keep the ports; pay for collection

B schedules the third-source access in the next ready step instead of adding a read port. The extra collection step costs 73,728 cycles relative to C over the full layer. This comparison describes the collection trade-off; it does not establish universal area superiority.

Keep the comparison on one question

All three designs retain the same five-stage pipeline, no-forwarding policy, arithmetic units, memory and software. Since A already supports four-lane INT8 dot products, 10.259% is not an overall speedup over scalar RV32I. The separate software-ablation percentage is not added to it.

Technical note · Why is the old destination also an input?

DOT4ACC can be written as rd ← dot4(rs1, rs2) + old(rd). The destination is both an output location and an accumulator input. Checking only rs1 and rs2 misses a dependency when an earlier instruction has not yet written back rd.

The integration includes old rd in RAW checks and completes collection before issue. Register aliases and x0 also need explicit handling: when operands share a register, the instruction must preserve the required old inputs, and zero-register behavior must remain consistent with the architecture.

This explains the integration constraint. The pending sequence describes collection once dependencies are ready; pipeline waits, execution and writeback still affect total instruction latency.

Scope & next steps

Results cover one complete convolution layer; full-network inference and board measurements remain future work.

Planned work asks whether the single-layer benefit carries into a complete model and onto physical hardware. End-to-end inference and board validation remain future work; current results do not establish full-network accuracy, end-to-end speedup or measured energy.

Technical record: contributions, methods & full results

Context

This undergraduate thesis studies how to integrate a three-operand fused instruction into a two-read-port register file. The controlled comparison uses two-port DOT4+ADD (A), two-port fused accumulation (B), and three-port fused accumulation (C), with a common five-stage pipeline, no-forwarding dependency policy, arithmetic unit, memory capacity, and software. Current results cover one complete model operator; board deployment has not been demonstrated.

My contribution

  • Implemented two-step operand collection and pipeline integration, including strict decoding, third-source RAW checks, holds and bubbles, register aliases, x0 semantics, reset cancellation, and MEM/WB writeback.
  • Built an A/B/C comparison that extends instruction checks to the complete op8 pointwise convolution of a public INT8 MobileNet VWW model, including CPU input/output copies, bias, exact requantization, and ReLU.
  • Implemented exact software requantization with four-step unrolling and evaluated its benefit separately in a fixed-hardware spatial-block experiment.

Methods & tools

  • Vivado 2022.2 / XSim; out-of-context synthesis, placement, routing, and 50 MHz timing checks for Artix-7 xc7a35tfgg484-2, using distributed register-file mapping and 32 KiB data RAM in all variants.
  • Pinned model and ten COCO image inputs; element-wise INT32 and INT8 checks for all 144 spatial positions and 294,912 scalar MACs, plus copy, packing, store, and corrupted-reference checks.
  • Retained firmware, source snapshots, waveforms, activity files, and reports; used matched-interval SAIF from post-route functional simulation for power estimation.

Evidence

  • Each architecture matched 92,160 INT32 and 92,160 INT8 values in RTL and selected mapped functional runs; all met the specified 50 MHz timing constraints.
  • Mean complete-layer times were 43.1202 / 38.6966 / 37.2220 ms for A/B/C. B reduced cycles by 10.259% versus A, a 1.1143× speedup; A already includes four-lane INT8 dot-product hardware.
  • B's estimated mean layer energy was 4.141 mJ, 9.917% below A. These are Vivado estimates from functional SAIF at 50 MHz, 25°C, and typical process, with some memory activity propagated by the tool; power and energy were not physically measured.
  • In a separate 4 KiB spatial-block experiment, exact requantization and unrolling reduced B's mean cycles by 39.893%. This software result is not combined with the full-layer architectural gain. The results do not establish whole-network inference, classification accuracy, or board-level measurements.
